# 留白计划双模式与极简推荐设计

**状态：** 待用户审阅

**日期：** 2026-09-20

**适用代码基线：** `D:\yxy1.0` 当前产品；本文件只记录设计，不代表功能已实现。

## 1. 目标与边界

目标用户是空闲时间不稳定、刚忙完且不想再做复杂决定的学生和上班族。改版后，用户可以在首页自行选择两种模式：

- **极简模式（新增、首页优先展示）：** 只输入可用时长和当前精力，马上得到一个能够在几分钟内开始的任务；可展开其他候选，也可直接选择休息。系统不监督任务完成。
- **完整模式（保持现有主流程）：** 继续填写条件、完成问卷、查看画像，获取候选任务和多任务排程，并使用现有执行与反馈闭环。

成功的关键不是增加任务数量，而是让短时用户迅速获得一条真实可做的建议，同时确保完整模式没有行为回归。两种模式共用 PostgreSQL、匿名用户身份、任务库、候选校验与偏好学习规则；它们不是两套独立产品。

本期仅使用现有任务库，不调用 DeepSeek 或其他模型，不需要模型密钥，也不消耗模型 Token。预留候选任务来源接口供未来接入 AI。登录、跨设备同步、实时地图/天气、执行监督、对极简模式做心理或医疗判断均不在本期范围内。

## 2. 已确认的产品决定

1. 首页由用户手动选模式，极简模式在视觉上优先，完整模式同样清晰可见；不按时长强制切换。
2. 极简模式只要求两项用户输入：`available_minutes` 与 `energy_level`。不要求选择分类或答问卷。
3. 未询问预算、出行和同行偏好时，极简模式只从**零预算、无需出门、可独自完成**的候选中选择。默认限制用于保证任务容易实行，不声称是用户表达过的偏好。
4. 首屏只展示一个首选任务；“查看更多”展开其余符合条件的不同候选。不提供单独的“换一个”按钮。
5. 极简任务必须提供简短推荐理由和“现在先做什么”的第一步。第一步是行动提示，不是新的表单步骤。
6. “直接休息”与首选任务同级。它不是跳过、未完成或低分。
7. 极简模式没有开始、完成、计时、截止提醒、评分或单任务执行页。用户可以自愿点“喜欢 / 不喜欢”，但不记录是否完成。
8. 两种模式共用同一匿名 `user_id` 的偏好学习；完整模式的历史可影响极简排序，极简的喜欢/不喜欢可影响完整模式排序。喜欢不等同于完成。
9. 将来两种模式都可使用同一个 AI 候选来源接口，输入信息各自不同；AI 候选必须经过后端校验。AI 超时或不合格时直接使用任务库，不弹出回退提示，也不把任务库结果称作“AI 生成”。

## 3. 用户流程与界面

### 3.1 极简模式

```text
首页选择极简模式
-> 输入可用分钟数和当前精力
-> 显示一个首选任务：名称、预计用时、简短理由、第一步
-> 可选择“查看更多”“喜欢 / 不喜欢”或“直接休息”
-> 离开或切换模式；无任务完成监督
```

“查看更多”展示本次推荐中的其余候选，最多与当前产品的 10 个推荐上限一致；若实际合格候选不足，只展示实际数量。列表中的每项均需有第一步和关键约束信息。用户从列表中选择其他项时，首选任务位置更新，列表内不出现重复任务。用户点“不喜欢”后，隐藏该任务并从现有候选前移下一项；若没有其他候选则显示空状态，不循环回刚被否定的任务。

“喜欢 / 不喜欢”是可选的轻量反馈；不点击也能正常使用。用户选择休息后，页面可结束本次推荐并留下一条中性事件，不展示失败或未完成提示。页面不能出现“AI 已为你生成”等与实际来源不符的文案。

### 3.2 完整模式与切换

完整模式保留当前创建会话、填写条件、快速/深度问卷、画像解释、10 个候选、排程、执行、反馈和历史页面及其接口形状。极简反馈可影响之后的排序，这是已确认的跨模式学习，不算完整模式流程回归。极简模式不绕过或伪造问卷提交，也不调用当前需要已提交问卷的 `generate_plan` 路径。

两个模式共用匿名用户身份，但各自的会话进度独立保存，避免极简输入污染问卷阶段。切换模式不删除另一个模式的草稿；用户已经明确输入的时长和精力可以作为切换后的默认值，仍需在完整模式确认。刷新页面后，当前模式及最近一次推荐能恢复。

## 4. 共用业务设计

### 4.1 信息汇总与候选来源

在推荐服务入口把两种模式输入标准化成 `RecommendationContext`：

| 字段 | 极简模式 | 完整模式 |
| --- | --- | --- |
| `user_id`、`session_id` | 复用现有匿名身份与会话机制 | 保持现状 |
| 时长与精力 | 当前用户明确输入 | 当前偏好、计划时间窗等 |
| 预算、出行、同行 | 固定保守限制：零预算、居家、独自可做 | 用户明确填写的限制 |
| 分类偏好 | 无必填；历史信息只作为辅助排序 | 已选分类及问卷画像 |
| 候选来源 | 本期任务库 | 本期现有任务库流程 |

定义窄接口 `CandidateProvider.generate(context) -> list[CandidateTask]`。本期提供 `TaskBankProvider`，从现有 `TaskRepository` 取候选。未来的 AI 适配器接收同一上下文、返回同一候选结构；本期不实现真实网络调用、不设置 AI 模式开关。现有本地 `mock` 测试模式保持原用途，不被误认为线上 AI。

候选统一包含任务 ID、标题、分类、建议分钟数、预算、地点/同行要求、负担指标、推荐理由及内部来源信息。`first_action` 对极简模式候选和未来 AI 候选为必填，对既有完整模式任务保持兼容。来源只用于日志与调试；前端无需显示回退提示。无论候选来自任务库还是未来的模型，硬约束校验和历史偏好学习均在提供者之外执行。

### 4.2 “马上能开始”的准入与排序

极简模式的硬准入条件：任务已审核、任务时长不超过可用时长、预算为零、无需出门、可独自完成、无需预约/购物/等人/特殊装备，且已经补齐具体的 `first_action`。首版只给经过人工核对的现有任务添加“可立即开始”标记与第一步，不把 700 个任务全部视为合格；完整模式仍可使用未标记的任务。

“最快能实行”指准备阻力低，不是简单按任务总时长从短到长排列。合格任务先按精力匹配、历史正负偏好和准备阻力排序，再以任务时长及稳定任务 ID 作为确定性择优依据。低精力优先轻松度高、体力与社交负担低的任务。没有历史时不假造画像；已有历史只作辅助排序，不改变本次输入和硬约束。

同一推荐结果内任务 ID 不重复。用户点击“不喜欢”后，后续推荐至少排除该具体任务；相似任务组需要重复负面信号才降权，不因一次点击就永久删除整类任务。候选不足时直接返回实际数量，不自动放宽零预算或居家限制。

### 4.3 反馈与历史

当前 `user_task_history` 的记录强制关联计划和计划项，现有 `task_feedback` 也只允许对计划项评分。极简模式不创建执行计划，因此不能伪造 `completed` 或计划项来复用这两张表。

在**同一个 PostgreSQL 数据库**中为极简模式增加轻量反馈事件，关联现有匿名 `user_id`、极简会话和任务 ID；事件类型限于 `liked`、`disliked`、`rest_selected`。`rest_selected` 无任务 ID，只作为中性选择，不参与任务负面计数。同一轮推荐对同一任务只保留最新一次喜欢或不喜欢，对休息只保留一次中性事件；重复点击不能把同一反馈累计多次。

共用的偏好汇总逻辑同时读取完整模式执行/评分历史和极简模式的自愿反馈，形成一致的任务与任务组权重。历史页面必须把“极简模式喜欢”与“实际完成任务”分开统计，不能把前者计入完成数。匿名身份只在当前浏览器持有；本期不承诺跨设备同步。

## 5. 建议的接口契约

- `POST /api/v1/sessions/{session_id}/quick-recommendations`：接收正整数 `available_minutes`、枚举 `energy_level` 和现有匿名 `user_id`；返回 `run_id`、一个 `primary_task`、零到九个 `alternatives`、实际使用的保守限制。相同输入且偏好未变化时可恢复同一轮结果；反馈改变偏好后，下一轮请求可重新排序。
- `GET /api/v1/sessions/{session_id}/quick-recommendations/latest`：刷新后恢复最近一轮结果。若不存在，返回明确的空状态，不自动生成新任务。
- `POST /api/v1/sessions/{session_id}/quick-recommendations/{run_id}/feedback`：只接受 `liked`、`disliked` 或 `rest_selected`；前两种要求任务确属该轮推荐，休息不附任务 ID，并幂等保存。不存在 `start` 或 `complete` 动作。

所有接口继续使用项目现有 `success(data)` 响应封装和异常格式。推荐轮次与反馈均写入同一 PostgreSQL 数据库；反馈必须校验推荐轮次与路径中的会话一致，不向前端暴露内部来源日志或数据库细节。现有匿名 `user_id` 不是安全登录凭证，本期不据此承诺跨设备或强身份保护，也不新增任意 `user_id` 的历史读取入口；后续若增加账号体系，需要统一加强两种模式的授权校验。

## 6. 错误处理和验收

| 场景 | 预期行为 |
| --- | --- |
| 时长或精力输入无效 | 返回清晰的字段错误，不执行筛选。 |
| 没有合格的立即可做任务 | 显示“当前条件下暂无合适建议”、直接休息和返回修改时长入口；不凑数、不突破硬限制。 |
| 候选少于 10 个 | “查看更多”只展示实际候选，不循环展示首选项。 |
| 后端或数据库暂不可用 | 保留两项输入，停止加载，显示重试；不伪造推荐结果。 |
| 模式切换或刷新 | 草稿和已取得的推荐可恢复；完整模式的问卷、计划不受影响。 |
| 未来 AI 超时或不合格 | 后端使用任务库重新提供合格候选，内部记录来源；页面不额外提示，也不称其为 AI 生成。 |

上线前必须通过以下测试：

1. 单元测试覆盖极简硬约束、能否立即开始、精力排序、第一步非空、候选去重、历史权重、反馈幂等和无候选场景。
2. 用可替换的假 `CandidateProvider` 测试统一候选契约及未来 AI 失败后的任务库回退，不进行真实模型调用。
3. 数据库与 API 测试验证极简反馈落库、无伪造完成记录、两种模式之间的偏好影响，以及休息事件的中性语义。
4. 前端端到端测试验证极简模式从输入到首选建议、“查看更多”、休息、反馈、刷新恢复及切换模式。
5. 回归测试完整模式：问卷、画像、10 个候选、排程、执行、评分和历史统计保持可用。
6. 在真实手机或等效移动视口检查首屏可读、按钮可触达、无重叠；弱网测试无无限加载。

“打开到看到首个可用建议”的时间、无候选比例和喜欢/不喜欢比例应在试用阶段分别记录。先取得当前流程基线，再设置正式目标；不把用户未点击反馈解读为不满意，也不把休息解读为任务失败。

## 7. 按优先级实施

1. **P0：任务准入数据。** 为现有任务库中符合极简使用情境的任务核对立即可开始条件，补齐第一步，并建立覆盖不同可用时长/精力的测试样本。
2. **P0：共用候选边界。** 建立上下文与来源接口，先接现有任务库；保持完整模式现有行为，加入契约与回归测试。
3. **P0：极简推荐与轻量反馈。** 增加独立推荐入口和同库事件存储，复用匿名身份与共用偏好学习；不创建执行计划。
4. **P0：双模式前端。** 首页选择模式，极简结果只突出一个任务，其他放在“查看更多”，提供“直接休息”和自愿喜欢/不喜欢。
5. **P0：验收与回归。** 跑单元、数据库/API、前端移动端及完整模式主链路测试，修复问题后才发布。
6. **后续阶段：真实 AI 候选提供者。** 单独设计模型调用、密钥、费用、提示词和质量评估，再接入本期预留接口；不改变共同的硬约束校验与反馈语义。

## 8. 设计自查重点

- 极简模式不再出现“开始/完成/计时/超时”的 UI、API 或历史计数。
- 极简喜欢/不喜欢与完整模式的完成/评分语义不同，但最终都能影响推荐权重。
- “共用数据库和业务逻辑”不等于把极简反馈强行写成计划项；使用同库事件和共用汇总层。
- 只保留一个任务来源边界；未来 AI 不会要求重写排程、执行或反馈模块。
- 当前线上仍是任务库推荐；预留接口不代表 DeepSeek 已接通。
