# 用户测试与推荐效果指标设计

## 1. 文档状态

- 状态：待用户审阅
- 目标版本：第一阶段真实用户验证
- 适用对象：大学生测试用户
- 测试规模：20 名以上
- 测试周期：1 个月

## 2. 已确认的产品边界

本阶段只增加观测、反馈和管理员分析能力，不改变现有业务决策逻辑。

### 2.1 本阶段包含

- 为测试用户生成匿名编号，例如 `student_001`。
- 自动记录主流程行为事件。
- 用户完成任务后提交 1-5 分评价。
- 用户跳过或替换任务时选择原因，并可补充说明。
- 在现有 FastAPI 和 PostgreSQL 中保存测试数据。
- 增加管理员登录和单一管理员角色。
- 增加管理员专用数据看板。
- 根据验收指标输出第一阶段测试结论。

### 2.2 本阶段不包含

- 不接入 AI 大模型。
- 不修改任务推荐、相似任务排除、排程和执行的核心规则。
- 不修改任务库内容。
- 不为普通用户增加登录账号。
- 不增加普通用户可见的历史偏好页面。
- 不建立多角色权限系统。
- 不拆分新的统计服务。

## 3. 目标与验收标准

### 3.1 业务目标

同时验证两个问题：

1. 推荐任务是否符合用户当前需求。
2. 从创建会话到反馈的完整流程是否稳定可用。

### 3.2 验收指标

- 完整主流程成功率不低于 95%。
- 不出现阻断使用的严重 Bug。
- 完成任务后的平均评分不低于 4 分（5 分制）。
- 任务替换率低于 30%。
- 任务跳过率低于 30%。
- 所有指标都可以按测试周期和匿名用户编号查询。

## 4. 用户测试身份

### 4.1 匿名编号

客户端首次进入测试流程时生成匿名编号，格式为 `student_<随机编号>`。编号只用于区分测试样本，不包含姓名、手机号、邮箱或其他个人信息。

匿名编号随会话请求传递给后端，并在服务端进行格式校验。服务端拒绝过长、包含控制字符或疑似个人信息的标识。

### 4.2 数据保留

第一阶段只保存匿名行为数据和业务流程数据，默认保留 90 天。管理员可以在看板中删除某个匿名测试用户的观测数据，但不能删除正常业务所需的会话、计划和反馈记录。

## 5. 数据模型

采用新增观测表的方式，避免改变现有推荐和排程表的语义。现有业务表继续由原有模块读写。

### 5.1 `test_users`

| 字段 | 含义 |
|---|---|
| `id` | 数据库主键 |
| `anonymous_id` | 匿名测试编号，唯一 |
| `cohort` | 测试批次，例如 `student_2026_09` |
| `created_at` | 首次进入测试时间 |
| `last_seen_at` | 最近一次行为时间 |
| `deleted_at` | 匿名数据删除时间 |

### 5.2 `test_events`

| 字段 | 含义 |
|---|---|
| `id` | 事件主键 |
| `anonymous_id` | 匿名测试编号 |
| `session_id` | 关联业务会话，可为空 |
| `plan_id` | 关联计划，可为空 |
| `plan_item_id` | 关联计划项，可为空 |
| `event_type` | 受控事件类型 |
| `reason_code` | 跳过或替换原因，可为空 |
| `metadata_json` | 非敏感补充信息 |
| `occurred_at` | 客户端事件时间 |
| `received_at` | 服务端接收时间 |
| `idempotency_key` | 防止重复上报 |

允许的 `event_type` 包括：

```text
session_created
questionnaire_started
questionnaire_completed
recommendations_viewed
task_started
task_completed
task_skipped
task_replaced
schedule_adjusted
feedback_submitted
flow_error
```

允许的 `reason_code` 包括：

```text
not_interested
low_energy
not_enough_time
over_budget
location_inconvenient
too_difficult
not_matching_current_state
other
```

### 5.3 `task_test_feedback`

用于保存任务完成后的 1-5 分评价，不修改现有反馈模块的业务含义。

| 字段 | 含义 |
|---|---|
| `id` | 反馈主键 |
| `anonymous_id` | 匿名测试编号 |
| `session_id` | 关联会话 |
| `plan_item_id` | 关联任务 |
| `rating` | 1-5 分 |
| `comment` | 可选补充说明 |
| `created_at` | 提交时间 |

同一个 `plan_item_id` 只允许保存一条测试评价；重复提交使用幂等更新，不产生重复样本。

### 5.4 管理员表

第一阶段使用一个管理员角色，但仍使用独立管理员表保存账号和密码哈希。密码不进入代码、前端资源、日志或 Git 仓库。

管理员会话使用服务端签名的短期令牌或安全 Cookie。看板接口必须校验管理员身份，普通业务接口不能读取测试报表。

## 6. 数据流

```text
匿名用户进入产品
        ↓
生成 anonymous_id
        ↓
正常执行现有会话、问卷、推荐和排程流程
        ↓
前端异步上报行为事件
        ↓
后端校验并写入 test_events
        ↓
完成任务后提交 1-5 分评价
        ↓
写入 task_test_feedback
        ↓
管理员登录看板
        ↓
统计推荐效果和流程稳定性
```

观测接口失败时不能阻断主流程。事件上报失败只记录服务端日志或进入有限重试队列，不能导致用户无法查看任务、开始任务或提交业务反馈。

## 7. 接口设计

### 7.1 测试身份

```text
POST /api/v1/test-users/identify
```

用途：创建或恢复匿名测试用户。

请求字段：

```json
{
  "anonymous_id": "student_001",
  "cohort": "student_2026_09"
}
```

返回字段：

```json
{
  "anonymous_id": "student_001",
  "cohort": "student_2026_09"
}
```

### 7.2 行为事件

```text
POST /api/v1/test-events
```

请求必须包含事件类型、匿名编号和幂等键。服务端只接受白名单事件，不允许客户端任意写入统计字段。

### 7.3 任务完成评价

```text
POST /api/v1/test-feedback
```

请求包含匿名编号、会话、计划项、评分和可选说明。评分只能是 1 到 5 的整数。

### 7.4 管理员认证

```text
POST /api/v1/admin/login
POST /api/v1/admin/logout
GET  /api/v1/admin/me
```

登录失败时返回统一错误，不暴露账号是否存在。登录接口需要限流，连续失败后暂时锁定。

### 7.5 管理员指标

```text
GET /api/v1/admin/metrics/summary
GET /api/v1/admin/metrics/funnel
GET /api/v1/admin/metrics/recommendations
GET /api/v1/admin/metrics/reasons
GET /api/v1/admin/metrics/errors
```

所有指标接口支持以下筛选条件：

- `from`：开始日期；
- `to`：结束日期；
- `cohort`：测试批次；
- `anonymous_id`：单个匿名用户；
- `task_category`：任务分类。

## 8. 看板设计

看板只对管理员展示，包含以下区域：

1. **总体指标**
   - 测试用户数；
   - 会话数；
   - 完整流程成功率；
   - 平均任务评分；
   - 替换率；
   - 跳过率。

2. **流程漏斗**
   - 创建会话；
   - 完成问卷；
   - 查看推荐；
   - 开始任务；
   - 完成任务；
   - 提交反馈。

3. **推荐效果**
   - 各任务类别平均评分；
   - 各任务类别替换率；
   - 各任务类别跳过率；
   - 用户当前精力和推荐结果的关系。

4. **失败原因**
   - 固定原因排名；
   - 自由文本说明；
   - 流程异常接口和错误类型。

5. **测试用户明细**
   - 只展示匿名编号、批次和行为统计；
   - 不展示姓名、手机号、邮箱等个人身份信息。

## 9. 与现有业务的兼容原则

- 推荐模块继续使用现有任务库、过滤和去重逻辑。
- 排程模块继续负责时间冲突、预算和可用时段处理。
- 执行模块继续负责开始、完成和执行事件。
- 观测模块只监听业务结果并写入测试数据。
- 观测接口异常不得影响主业务接口。
- 数据库通过新增版本迁移创建新表，不覆盖现有数据。
- 前端只在现有流程节点增加轻量反馈和匿名标识逻辑。

## 10. 异常处理与安全要求

- 所有事件请求必须校验字段类型、事件白名单和幂等键。
- 事件上报失败不阻塞主流程。
- 管理员密码只保存哈希值。
- 管理员登录接口限流并记录失败次数。
- 管理员接口禁止通过前端参数绕过身份校验。
- 统计接口只返回聚合数据和匿名编号。
- 自由文本需要限制长度，避免写入脚本或超大内容。
- 事件元数据只允许业务白名单字段，禁止保存原始请求体。
- 数据库迁移必须可重复执行，且支持回滚或安全停用新功能。

## 11. 测试方案

### 11.1 单元测试

- 匿名编号生成和格式校验；
- 事件类型白名单；
- 跳过/替换原因校验；
- 评分范围校验；
- 幂等键去重；
- 指标计算公式；
- 管理员密码哈希和令牌校验。

### 11.2 接口测试

- 测试用户创建和恢复；
- 正常和非法事件上报；
- 重复事件上报；
- 完成任务后的评分提交；
- 未登录访问看板；
- 管理员登录后访问看板；
- 管理员退出后访问失效；
- 日期和匿名编号筛选。

### 11.3 集成测试

用独立测试数据库跑完整流程，验证业务表和测试观测表同时写入，且观测写入失败时业务流程仍然可以完成。

### 11.4 端到端测试

至少覆盖：

```text
创建会话 → 完成问卷 → 查看推荐 → 开始任务
→ 完成任务 → 提交评分 → 管理员看板查看数据
```

同时覆盖：

```text
查看推荐 → 替换任务 → 选择替换原因 → 看板统计替换率
查看推荐 → 跳过任务 → 选择跳过原因 → 看板统计跳过率
```

## 12. 实施后的交付物

- 数据库迁移文件；
- 测试用户和事件存储模块；
- 事件和评价接口；
- 管理员认证接口；
- 管理员指标接口；
- 开发者数据看板；
- 单元、接口、集成和端到端测试；
- 测试使用说明和指标口径说明；
- README 中的启动和测试步骤更新。

## 13. 第一阶段完成定义

只有同时满足以下条件，才认为本阶段完成：

1. 20 名以上大学生可以在 1 个月测试周期内使用主流程。
2. 行为事件、完成评价和跳过/替换原因能够稳定写入数据库。
3. 管理员可以登录看板并按筛选条件查看指标。
4. 观测系统异常不会阻断原有业务流程。
5. 自动化测试通过，且完整流程成功率达到 95%。
6. 测试结果能够判断平均推荐评分、替换率和跳过率是否达到验收标准。
