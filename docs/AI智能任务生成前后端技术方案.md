# 留白计划：AI 智能任务生成前后端技术方案

状态：设计稿，供确认；本文不代表功能已经实现。

## 1. 目标与边界

用户完成兴趣选择、条件填写、问卷和偏好画像后，后端把这些步骤及可用历史反馈整理为一次生成上下文。AI 只负责两件事：先根据上下文写出结构化的任务生成说明，再生成带有理由的推荐任务。后端负责核对说明、校验并保存任务，随后独立完成排程、执行、反馈和历史记录。AI 不生成起止时间、不改变执行状态，也不自行写入反馈。

本方案的任务内容完全由 AI 生成。原有公开任务库不参与首次生成、更换、调整或失败补足。问卷题库继续用于收集偏好；既有画像规则、排程器、执行和反馈模块仍承担各自职责。一次正常生成目标为 10 个互不重复的推荐任务；受时间限制，部分任务可以处于“待安排”状态。

## 2. 现状与改造范围

现有前端是六步单页流程：兴趣方向、条件、问卷模式、答题、画像解释、计划结果。`frontend/app.js` 调用 `frontend/api.js` 的 `generatePlan()`；`main.py` 将请求交给 `MVPOrchestrator.generate_plan()`。当前编排器在画像后从 `TaskRepository.search_tasks()` 取候选，调用 `recommend_tasks()`，再调用 `build_schedule()`。

现有“换一个”“更轻松”“加入时间线”等操作也从公开任务库查找 `task_id`，因此不能只替换首次推荐函数。生成任务的持久化、查找、替换、反馈和历史分析必须一并切换到 AI 任务来源。本文按当前接口设计演进，不要求重做前端页面或更换 PostgreSQL。

## 3. 总体架构

```text
前端六步收集信息
  -> FastAPI 会话与问卷接口 -> PostgreSQL
  -> 确定性画像与画像解释
  -> ContextBuilder 汇总用户上下文
  -> BriefWriter（模型调用 1：写生成说明）
  -> BriefValidator（后端核对说明）
  -> TaskGenerator（模型调用 2：生成任务、生成理由、推荐原因）
  -> TaskValidator（后端校验、去重；必要时定向重试）
  -> GeneratedTaskRepository（持久化）
  -> AI 职责结束，交给现有 Scheduling / Plan / Delivery 链路
  -> 后端执行与反馈服务记录后续行为
  -> 前端展示 10 个推荐、各项理由与时间线
```

第一版采用后端编排的双阶段工作流，不需要多智能体框架或让模型自主访问数据库。`BriefWriter` 与 `TaskGenerator` 可使用同一模型，但承担不同任务；后端始终控制阶段顺序、调用次数和数据读写。用户的执行、跳过、替换及评分由后端保存，只有下一次需要生成任务时才作为上下文提供给 AI。

## 4. 所有前置步骤如何进入提示词

| 前置步骤 | 原始证据 | 结构化输入 | 优先级 |
| --- | --- | --- | --- |
| 兴趣选择 | 用户选中的方向 | `selected_categories` | 本次明确意愿 |
| 条件填写 | 时间、预算、出行、同行、天气、精力、心情、节奏、城市或校园 | `hard_constraints` 与 `current_context` | 硬限制优先 |
| 问卷模式 | quick 或 deep | `questionnaire_mode` | 解释证据覆盖程度 |
| 问卷作答 | 题目 ID、题干、维度、分值、跳过状态、反向计分标记 | `questionnaire_evidence` | 偏好证据 |
| 画像解释 | 各维度分数、排序、可信度、约束卡片和说明 | `profile_snapshot` | 偏好总结 |
| 历史与反馈 | 完成、跳过、替换、低分和显式排除项 | `history_preferences` 与 `excluded_signatures` | 明确排除高于倾向 |
| 本次时间窗口 | `free_start`、`free_end`、计划密度、已出现任务 | `generation_goal` | 排程边界与去重 |

后端读取已保存的会话数据和提交后的问卷快照，不相信前端临时拼出的“完整提示词”。输入给模型时同时保留原始答案和确定性画像摘要；跳过题记为“未知”，不能转写为反对。空历史记为“无历史证据”，不能编造长期偏好。可选地点只有用户提供的粗粒度位置；没有实时地点服务时不得断言店铺存在、营业或准确价格。

优先级固定为：安全与显式排除 > 预算、时间、出行等硬条件 > 本次明确选择 > 当前状态 > 问卷画像 > 历史软偏好 > 多样性。发生冲突时不由模型自行放宽高优先级条件。前端画像页展示的是当前画像；模型实际使用的上下文快照要与用户点击生成时的会话版本一致。

## 5. AI 自写生成说明与提示词边界

固定的服务端指令定义任务标准、优先级、输出结构和禁止事项，代码维护并记录版本。第一次模型调用只产生 `GenerationBrief`，包含：必须满足、优先满足、禁止推荐、未确认信息、分类覆盖目标、任务数量、预计负担与任务组成原则，以及每条要求引用的输入来源；不让 AI 制定具体起止时间。

`GenerationBrief` 是模型生成的数据，不是新的 system 指令。后端对照原始上下文检查：硬限制是否原样保留；是否把跳过题解释成偏好；是否遗漏低分排除项；是否凭空增加用户身份、地点或预算。失败时只允许一次定向修正，仍不合格则停止并返回可理解的错误。

第二次模型调用接收服务端固定规则、通过检查的生成说明和必要的原始证据，产出任务及逐项理由。结构化输出可约束字段和类型，但不能证明现实可行性，因此仍须后端验收。提示词和响应模板均记录版本，便于复现与比较。

## 6. AI 任务的数据契约

模型输出任务字段：`title`、`category`、`action_steps`、`duration_minutes`、`estimated_budget`、`outing`、`company`、`ease_level`、`physical_load`、`social_pressure`、`location_dependency`、`generation_reason`、`recommendation_reason`、`evidence_refs`、`uncertainty_note`。`generation_reason` 解释为什么根据本次输入构造这一具体活动；`recommendation_reason` 用用户能读懂的话解释它为什么适合此人的当前条件。`evidence_refs` 指向兴趣选择、条件、问卷回答、画像或历史反馈的真实来源，不能引用跳过题作为确定偏好。后端生成稳定 `task_id`，并补充 `session_id`、`generation_id`、`semantic_signature`、`status` 和时间戳；模型不得自称任务已通过校验。

兼容现有前端时，返回的每个推荐任务继续包含 `id`、`title`、`category`、`duration`、`budget`、负担信息，以及通过校验的生成理由、推荐原因和依据来源。旧的 `reason_text` 可映射到推荐原因以兼容现有卡片；新字段单独保留，避免混淆。“推荐依据”应具体到用户选择或回答，例如“你选择了居家、低预算且目前精力较低”，不能只写“适合你”。`recommendation.tasks`、`task_ids`、`recommended_task_count`、`plan` 和 `delivery` 的外层结构保持不变。前端现有“推荐可信度”数值不得由模型自行编造；没有经过校准的量化指标时改为展示可核对的推荐依据。

校验分为四组：

1. 结构：必填字段、枚举、数值范围、文本长度、恰当分类。
2. 硬约束：单项预算与总预算、单项时长与时间窗口、出行和同行限制、低精力的体力上限、明确排除项。
3. 质量与解释：动作具体、可独立开始、无危险或需要专业指导的表述、无未经验证的店铺和价格事实；两种理由均非空，`evidence_refs` 均存在于本次上下文中，理由不能与用户条件或答案相反。
4. 去重：`task_id`、归一化动作签名、地点与动作组合，以及本会话曾出现任务的语义相似检查；更换任务必须排除当前任务及其历史版本。

被拒绝的任务只携带失败原因进入至多一次定向补写。没有足量合格任务时返回实际可用数量和缺口原因，不从旧任务库补齐，也不伪造十项结果。

## 7. 后端模块与接口

新增边界：`AIModelClient` 负责供应商调用、超时和用量回传；`GenerationContextBuilder` 只读取会话、问卷、画像和历史；`GenerationBriefService` 负责第一阶段；`AITaskGenerationService` 负责第二阶段与一次补写；`GeneratedTaskRepository` 管理持久化；`GenerationValidator` 不依赖模型、可独立测试。模型供应商由配置决定，首选阿里云百炼的兼容接口，模型 ID 和 API Key 由服务端环境变量提供；供应商切换不改变领域数据契约。

`POST /api/v1/sessions/{session_id}/plan/generate` 保持前端调用方式。内部顺序调整为：校验会话与问卷 -> 建立/读取同版本画像 -> 构建上下文快照 -> 两阶段模型调用（任务与逐项理由）-> 后端校验 -> 事务保存 AI 任务与生成记录 -> 后端调用现有排程器 -> 保存计划和网页交付。AI 的输出到“推荐任务”即止；起止时间、执行状态和评分均由后端模块处理。使用请求幂等键或“会话 + 画像版本 + 时间窗口 + 密度”的生成键，避免用户重复点击产生两套任务与双倍费用。

`GET /api/v1/sessions/{session_id}/plan` 继续读取已保存的计划。现有推荐调整、计划项替换、换轻松任务、加入时间线和重新排程接口沿用现有 URL，但查询来源改为 `GeneratedTaskRepository`；“换一个”或“更轻松”需要新内容时，由后端携带当前条件、历史任务签名和调整方向再次请求 AI 生成一个带理由的新任务，随后由后端校验、替换和排程。无需新任务的时间调整、开始、完成、跳过、反馈与历史记录不调用 AI，继续使用稳定的 `task_id`。

错误契约保留现有 `{data, error}` 包装，建议区分 `ai_not_configured`、`ai_rate_limited`、`ai_timeout`、`ai_invalid_output`、`insufficient_valid_tasks`、`constraint_conflict`、`database_unavailable`。模型供应商的原始错误、Key 与完整个人上下文不返回给前端。

## 8. PostgreSQL 数据设计

- `ai_generation_runs`：生成 ID、会话 ID、用户 ID、画像/问卷版本、上下文快照或安全摘要、生成说明、提示词版本、供应商、模型、阶段状态、校验结果、Token 用量、耗时、错误类型、创建时间。
- `generated_tasks`：稳定任务 ID、生成 ID、会话 ID、任务字段、生成理由、推荐原因、依据来源、语义签名、校验状态、产生来源（首次、替换、调整、补写）、创建时间。
- `task_exclusion_signatures`：会话内显式排除、替换历史和低分不再推荐的任务签名；已有记忆表可承载的字段优先复用，避免重复事实源。

`plan_items.task_id` 继续引用稳定任务 ID；读取任务详情时先按该 ID 查询 AI 任务记录。现有计划项保留标题与类别快照，历史页面即使模型任务后来失效也能复现当时的内容。删除会话数据时同步清理其生成记录和任务；跨设备历史只有在有可信账号认证后才按用户聚合，不能仅凭浏览器传来的 `user_id` 授权读取他人数据。

## 9. 前端交互与状态

保留现有六步和像素视觉：兴趣选择 -> 条件 -> 问卷模式 -> 答题 -> 画像 -> 结果。前五步的数据继续通过当前接口保存。画像页点击“生成计划”后进入明确的生成状态：整理偏好、生成任务、校验与排程；这些文案反映后端阶段，不展示模型的内部推理或 API Key。

生成期间禁用重复提交，但刷新或重新打开页面后通过会话恢复生成结果。结果页仍显示十个推荐位与已排入时间线的子集；不满十项时显示实际数量和原因。每张卡片展示具体动作、推荐原因、时长、预算、负担和“不确定”提示；详情中展示生成理由与对应的用户输入依据，让用户能核对推荐是否理解了自己。模型失败时保留已填写条件和问卷答案，用户可以重试；若条件互相冲突，清楚指出冲突的两项，让用户自行修改。展示理由可提高可解释性和纠错能力，是否提高实际匹配质量仍需用反馈数据验证。

“换一个”和偏好调节按钮发出当前 `task_id`、调整意图和当前计划版本；后端依据持久化的排除记录生成新任务。前端不负责排重，也不依赖 `localStorage` 中的任务列表作为最终事实。历史页面只解释真实记录，不把模型推测当作用户已经表达的偏好。

## 10. 部署、成本与数据保护

本地后端与 Vercel Python 函数均通过服务端环境变量读取模型 Key、模型 ID、Base URL 与超时配置。API Key 不进入 `frontend/`、GitHub、响应体或日志。Vercel 线上环境需要配置同一组变量并重新部署；PostgreSQL 仍由现有 `SESSION_DATABASE_URL` 指向线上数据库。模型调用受函数运行时间限制，按实测耗时配置合理超时。

单次生成通常至少两次模型请求；补写和每次“换一个”会增加用量。记录每次调用的输入/输出 Token、失败率与成本估算，限制每会话生成频率和单日调用量。若使用百炼免费额度，先在控制台核对支持结构化输出的具体模型和当前额度，测试阶段开启免费额度用完即停。免费额度耗尽或服务不可用时给出明确错误，不暗中切换为旧任务库。

仅发送生成所需的最小信息到模型：偏好与粗粒度地点足够时，不上传姓名、联系方式或完整敏感历史。用户输入属于低信任数据，不能改变服务端规则。保存必要的版本和校验信息，限制原始提示词的保留时间；记录日志时遮蔽密钥与个人数据。

## 11. 测试与验收

后端单元测试覆盖上下文来源、优先级、跳过题、生成说明的硬约束核对、格式与业务校验、预算总和、语义排重、逐项理由的真实性和无旧库回退。用可控的假模型响应测试超时、限流、空输出、重复任务、虚构依据、补写失败和幂等请求。接口测试覆盖生成、恢复、换一个、加入时间线、执行、反馈与历史记录，并断言时间调整、执行和反馈不会触发模型调用。

端到端测试至少包含：低预算却偏好高消费、低精力但选择运动、完全居家、跳过多数问卷题、用户明确排除同类任务、连续多次更换、时间不足十项、模型不可用。验收门槛：硬约束违规任务为零；每个展示任务都有可核对的生成理由、推荐原因和真实依据；当前会话内已替换的同一任务不重新出现；任何展示任务均能通过 `task_id` 找到持久化记录；用户刷新后计划不丢失；在无合格任务时如实报错。推荐满意度、完成率和跳过率用线上反馈持续评估，不能仅凭理由文字或结构化输出声称准确率得到保证。

建议先在本地用假模型通过全链路测试，再用真实模型和少量匿名测试会话做人工检查，最后发布到 Vercel。发布后监测生成成功率、验证拒绝率、调用耗时、Token 成本和用户反馈；每次提示词或模型版本变化都复跑固定样例。

## 12. 建议实施顺序

1. 冻结接口契约和 AI 任务字段，建立数据库迁移与模型调用适配层。
2. 完成上下文汇总、生成说明、AI 任务生成和确定性校验。
3. 将首次生成接入 `MVPOrchestrator`，保留现有前端响应结构。
4. 改造换任务、调整、加入时间线、反馈和历史链路，使其只引用 AI 任务记录。
5. 补齐前端生成状态、错误恢复和真实推荐依据展示。
6. 先用假模型完成回归测试，再进行真实模型成本与质量验收，最后上线。
